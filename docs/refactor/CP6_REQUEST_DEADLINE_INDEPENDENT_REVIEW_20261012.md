# 请求预算独立审查

日期：2026-10-12。审查对象为本轮最终稳定的请求预算实现。此报告仅记录独立静态源码审查；审查者未运行 Maven、未调用真实供应商、未写外部 PostgreSQL 或 Redis。实施者和主线程的测试成绩不作为本报告自行执行的证据。

## 结论

在本轮修改范围内，未发现确定的阻断缺陷。这不是完整端到端性能验收，也不证明不存在其他问题。真实首次冷请求仍需独立实测。

## 源码核验

- `OperationDeadline` 使用单调时钟；嵌套作用域采用较早截止时间，`close` 恢复旧值或移除 ThreadLocal。`carry` 在异步任务中通过 try-with-resources 恢复执行线程原上下文，未发现线程复用泄漏路径。
- `PlannerService.createInternal` 在 `prepare` 之前建立作用域。空计划且预算耗尽时，在 `repository.create` 之前返回 504；动态计划不会因此重新回退全城计划。非空结果统一写入超时降级原因、用户可读说明及部分完成状态。
- 高德编排、HTTP、路线 hydration 与文案任务显式传播预算。高德自有 HTTP 池使用 `AbortPolicy`，提交拒绝归一化为领域不可用，不再同步执行 HTTP。实际注入文案服务的 `plannerLlmExecutor` Bean 同样使用 `AbortPolicy`，拒绝时降级模板。
- 缓存 follower 的限时等待不会取消共享 owner Future。POI 与天气边界将等待异常归一化为领域结果，避免未处理异常直接成为 500。
- 异步供应商任务只返回结果；行程、站点和地图信息由等待线程同步更新。未发现超时后的迟到结果异步写回行程或发布规划会话的路径。底层已经发出的 HTTP 可能继续运行，不能据 Future 取消宣称供应商请求停止。
- 从避免过度防御的角度，本轮保留单一预算上下文与必要调用边界，未发现必须移除的重复包装。自有 HTTP 池直接使用拒绝策略，比线程身份判断更直接。

## 保留边界

- 实际 hydration 池仍采用 `CallerRunsPolicy`。同步执行的 `routePair` 受同一请求剩余预算约束，但不能宣称 hydration 单独具有 15 秒硬上限。
- 创建幂等锁等待在 scope 之外；数据库查询、保存和响应传输未新增截止机制。BFF 独立 RAG 不受 Java ThreadLocal scope 覆盖。
- 自动建立预算的是 create 路径；shadow、replan、局部调整仍沿用原有行为。不能泛化为所有入口均有 45 秒或完整端到端 60 秒硬保证。
- 不以本次源码审查代替真实 PostgreSQL、Redis、多实例、服务自身崩溃恢复或真实冷启动供应商验收。
