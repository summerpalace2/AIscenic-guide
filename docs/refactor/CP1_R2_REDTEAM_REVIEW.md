# CP1-R2 red-team review

Date: 2026-10-09

## Verdict

**FAIL — do not accept CP1 yet.** The frozen R2 candidate fixes the previously reported single-process scheduling interleavings by holding a per-stripe monitor across L1 and L2 read/write/delete operations. However, the delete-exception path can make a removed proposal readable again after local cache loss, and Redis deserialization does not validate the restored object's ID against the requested key. Expired `put` also does not invalidate an older L2 value for the same ID. No source or existing document was changed for this review.

## Required closure before acceptance

1. Define and enforce cancellation/remove behavior when Redis delete fails. At minimum, a failed delete must not silently permit subsequent L2 restoration and apply; use a durable/epoch guard or fail closed until deletion is confirmed. Add a test that makes delete throw, clears/reconstructs L1, and proves apply causes no DB write.
2. Define expired `put` semantics for an existing ID and prevent a stale prior L2 snapshot from being restored after the expired write.
3. Validate restored snapshot identity (`proposalId` equals the requested Redis key) and required fields / plausible absolute expiry before caching or applying; add malformed, missing-field, mismatched-ID and extreme-expiry tests with no DB side effect.
4. Add the Redis TTL argument and absolute-expiry boundary cases to contract tests. If real Redis is unavailable in CP1, retain that limitation explicitly rather than describing the adapter as integration-verified.
