## 用户提出的结构问题：源码裁决

1. **宠物是专用实现，属实。** EvidenceRequirement包含petPolicy/guideDogPolicy/ordinaryPetPolicy，并为宠物入场规则写专门语法。当前没有“任何属性都要求对应证据”的通用机制；新政策不应继续逐项加Java布尔字段。
2. **严格字面主体有局限，属实。** 现有Attraction没有独立的实体identity aliases字段；旧AttractionAliasMatcher同时注册地图keywords/matches/alternatives，以及关联型分类别名，不能直接作为证据身份注册表。数据别名本身不是代码硬编码，但必须区分真同义名与附近地点/区域/路线组合。本集3条显式别名题通过，是因为片段正文已经说明别名，并未验证目录驱动别名能力。
3. **UNKNOWN缺少独立背景通道，属实。** 前置QUERY_GATE没有做知识检索，facts与citations为空。ChatRetrievalCoordinator仅收集facts，状态主要由verified决定；ChatApplicationService/ChatPromptContextAssembler在无上下文时传入检索不可用提示。附近/目标POI可能另行补上下文，但没有明确的“主结论未知、背景资料可参考”契约。本轮只读核验该调用链，未运行真实聊天或保证最终用户文案。

## 调整后的实施顺序与退出条件

1. 先建立通用主体—属性需求检查。将政策/设施/票价等识别词与规则放外置资产，核心代码遍历需求集合；未知属性不能因为命中文档就自动认定可答。对于无法确定的语义关系保留UNKNOWN，不能用新的全文关键词重叠伪称蕴含判断。宠物/导盲犬作为数据实例保留适用范围差异。
2. 建立目录中独立、可审阅的实体别名字段及城市内身份解析，只采用规范名/同一实体真别名；冲突或关联型词不自动合并。门禁读取该数据边界；不把地图搜索候选当identity。现实目录别名需来源复核。
3. 设计UNKNOWN与背景参考的分离契约。若补检索，单独记录backgroundSource、用途与引用，禁止背景支撑被拒绝的主结论；官方渠道或电话只能来自实际资料，不编造联系方式。不再把“知识不足”混成系统故障。
4. 当前25题从此进入回归集。修复后可用同集作配对重测，但不可再叫未见验证；另由独立出题人冻结新保留集。人工复核失败和抽样通过标签仍未完成。
5. 上述边界闭合后进入确定性多轮续接，随后才做主链路本地模型/混合检索实验。
