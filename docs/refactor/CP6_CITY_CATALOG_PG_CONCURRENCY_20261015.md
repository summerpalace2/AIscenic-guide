# CP6 city catalog PostgreSQL concurrency acceptance

`CityAttractionCatalogImporter.refresh` now starts a database transaction before loading a catalog snapshot. PostgreSQL instances serialize at the existing singleton `attraction_catalog_revision` row with `SELECT ... FOR UPDATE`; SQLite retains its compatibility path by taking its writer lock with a no-op revision update. The importer reads and validates the configured classpath/external files only after obtaining that lock, then compares the content fingerprint, applies owned-row changes, updates `verified_fields`, and advances the revision in the same transaction. A malformed batch rolls back without replacing the previous catalog.

The fingerprint is content identity, not a version ordering mechanism. The database lock orders installations against one shared authority; it cannot decide which of two different external directories, classpath bundles, or old application artifacts is newer. All instances allowed to refresh one database must therefore use the same immutable, versioned catalog release. Publish a new release atomically and roll all refreshing instances to that release; disable refresh on nodes that do not share that source. Divergent sources are an operator/configuration error and are not automatically reconciled.

`AttractionAliasMatcher` observes the shared catalog revision and rebuilds its local alias index when an importer commits. The opt-in `Cp6CityCatalogImporterIntegrationTest` uses the existing `CP6_IT_*` disposable PostgreSQL target, creates and drops a random schema, and launches two independent JVM workers. It checks a single revision increment for identical concurrent imports, post-update visibility in two consumers, preservation after a malformed batch, and alias invalidation after rename and deletion. It does not establish automatic ordering for divergent source directories or prove file-level atomicity if an operator edits an active directory in place; deployments should replace immutable release directories atomically.
