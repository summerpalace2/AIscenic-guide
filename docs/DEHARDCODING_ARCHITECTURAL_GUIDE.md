## 一、 架构彻底反省与核心定性

### 1.1 过去犯下的致命错误
在之前的迭代中，系统多次陷入了**“出现误判 -> 在 Java 中加正则/补白名单 -> 换个词又失效 -> 再加正则”**的恶性死循环（例如：为了防教学楼误判加四教正则，发现漏了科技楼又加科技楼正则，发现西班牙海鲜炒饭被截断就机械放宽字符限制）。

### 1.2 为什么“规则代偿”是绝对的死路？
- **无限的现实 vs 有限的代码**：中华美食有数万种菜名，全国有 3000 所大学、数千万栋建筑，地理 POI 更是过亿。试图用 Java 字符串和正则表达式去穷举现实世界，属于典型的反智工程反模式；
- **违反开闭原则（OCP）**：每增加一个地名、菜品、品牌，就必须修改 Java 源码、重新编译并重启服务；
- **职责倒置反模式**：Java 规划引擎的唯一合法职责是**“时空约束拓扑求解（Spatio-temporal Solver）”**，它却越权去扮演“自然语言理解（NLP）”和“地理行业知识库（LBS GIS）”。

## 三、 彻底治本的四大架构改造范式

```
                   【彻底去硬编码的现代工业级分层架构】

 1. 用户输入 ─────────► [ LLM 规划大脑 (NER) ]
                         │  - 零样本抽取：风味实体、意图类型、时间倾向
                         │  - 产出标准结构化 DTO (0 行 Java 正则)
                         ▼
 2. 实体定性 ─────────► [ 高德 LBS 开放平台 (TypeCode First) ]
                         │  - TypeCode 以 05 开头 -> 100% 权威餐饮
                         │  - TypeCode 以 11 开头 -> 100% 权威景区
                         │  - TypeCode 以 14/20 开头 -> 100% 公共设施噪声
                         ▼
 3. 空间拓扑 ─────────► [ 动态地理中心与质心求解器 ]
                         │  - 有站点：凸包球面质心 (Centroid)
                         │  - 冷启动：高德地理编码动态获取城市行政中心 (0 经纬度魔数)
                         ▼
 4. 时空求解 ─────────► [ Java 规划引擎：纯数学时空约束拓扑求解 ]
                         │  - 基于当天游览间隙 (Gap Solver) 动态寻找最佳就餐时段
                         │  - 核心代码无一行菜名、无一行人名、无一行特定地名！
```

### 范式 1：高德行业标准代码权威定性（TypeCode First）
- 高德官方规定：
  - `05xxxx`：餐饮服务（中餐、快餐、咖啡、茶艺、小吃等）
  - `11xxxx`：风景名胜（公园、景点、名胜古迹等）
  - `14xxxx`：科教文化服务（学校、科技楼、教学楼、科研所等）
  - `20xxxx`：公共设施（公厕、变电站、垃圾站等）
- **改造后代码准则**：
  直接判定 `typecode`，彻底移除所有 `FAMOUS_PERSONS`、`NOISE_NAME_KEYWORDS`、`GENUINE_SCENIC_SUFFIXES`。

### 范式 2：LLM 零样本结构化实体识别（Zero-shot NER）
- 自然语言理解全部交还给大模型，Prompt 契约定义：
  ```json
  {
    "intent": "ADD_DINING",
    "cuisine_or_place": "正宗西班牙海鲜炒饭",
    "is_generic_craving": true,
    "time_window": "LUNCH"
  }
  ```
- 后端 Java 废除所有手写食物词根正则，直接根据 DTO 中的结构化字段发起高德搜索。

### 范式 3：消除所有经纬度魔数（Dynamic Geo-Centroid）
- 严禁在代码中出现 `"106.577000,29.556000"` 或其他任何城市的写死坐标；
- **几何质心算法**：
  若当天已有站点，计算所有站点的经纬度均值；若跨度过大锚定最新游览点；
- **冷启动动态地理编码**：
  若当日完全无站点，调用 `routeService.searchPoi(cityName + "市政府", cityName)` 或高德行政区划接口动态获取中心坐标，实现全国各城市通用。

### 范式 4：动态时钟间隙求解（Temporal Gap Solver）
- 废除写死固定时间（08:00、12:00、18:00）；
- 引入生理用餐时段区间：
  - 午餐区间：`[11:30, 13:30]`
  - 晚餐区间：`[17:30, 19:30]`
- 在行程站点的已占时间块中扫描空隙，自动选择前后路线耗时最平滑的间隙插入。

### 范式 5：配置与数据资产外置（External Taxonomy SPI）
- 所有品牌库、菜系风味字典、城市默认策略，一律放置在 `resources/taxonomy/` 下的 `.json` 或 `.yml` 文件中；
- 核心代码只面向 `TaxonomyPort` 接口编程，支持运维热更新与多城市配置热插拔。

## 四、 协同分工与执行流水线

1. **智能体 A（实施工程师）**：
   - 严格按照本指引中的 14 处罪证清册逐一进行物理重构；
   - 彻底删除写死的人名、地名、食物正则、经纬度魔数与时钟固定点；
   - 编写与更新对应的单元测试，确保全量测试通过。
2. **智能体 B（架构审计师）**：
   - 使用静态分析脚本（grep/regex）扫描全工程，检查是否还遗留任何经纬度魔数、名人名单或写死地名；
   - 审查代码是否真正满足开闭原则与 DIP 依赖倒置。
3. **智能体 C（红方对抗质检官）**：
   - 模拟北京、杭州、西安、武汉等不同城市的真实用户请求；
   - 构造偏门美食（“驴肉火烧”、“螺蛳粉”）、生僻高校建筑（“蒙民伟理科馆”）、超长复合自然语言，发起全面实弹攻击；
   - 验收系统是否实现真正的 0 硬编码动态泛化。
